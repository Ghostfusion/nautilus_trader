# 04 - Sample data

This lecture describes the two committed CSV files, shows how to read them, and shows how to
inspect them with real output.

## 1. What the data is

The manual commits two files under `sample_data/`:

| File                                          | Rows | Venue   | Instrument             |
| --------------------------------------------- | ---- | ------- | ---------------------- |
| `sample_data/btcusdt_perp_binance_quotes.csv` | 240  | BINANCE | `BTCUSDT-PERP.BINANCE` |
| `sample_data/btcusdt_perp_bybit_quotes.csv`   | 240  | BYBIT   | `BTCUSDT-PERP.BYBIT`   |

They describe the **same underlying** on two venues, over the same 240 one-second intervals. This
is the smallest dataset that can carry a cross-venue basis: two prices of the same thing at the
same instant, at two different venues.

The data is **synthetic**. It is not a recording of Binance or Bybit. It was generated by the
deterministic generator printed in `sample_data/README.md`, which uses only `math` and `csv` from
the standard library. No network access, no randomness, and the same bytes on every run.

## 2. The columns

| Column        | Unit                                           | Meaning                                      |
| ------------- | ---------------------------------------------- | -------------------------------------------- |
| `ts_event_ns` | integer nanoseconds since 1970-01-01T00:00:00Z | When the quote happened.                     |
| `bid_price`   | USDT per BTC, one decimal                      | The best buy price. You sell at this price.  |
| `ask_price`   | USDT per BTC, one decimal                      | The best sell price. You buy at this price.  |
| `bid_size`    | BTC, three decimals                            | Quantity resting at the bid in this fixture. |
| `ask_size`    | BTC, three decimals                            | Quantity resting at the ask in this fixture. |

The first data row of each file, verbatim from the committed files:

```csv
ts_event_ns,bid_price,ask_price,bid_size,ask_size
1700000000000000000,63999.5,64000.5,1.000,1.000
```

```csv
ts_event_ns,bid_price,ask_price,bid_size,ask_size
1700000000000000000,64054.2,64055.8,1.000,1.000
```

The first line is the BINANCE file, the second the BYBIT file. Same timestamp, different prices:
`mid_BINANCE = (63999.5 + 64000.5) / 2 = 64000.0` and
`mid_BYBIT = (64054.2 + 64055.8) / 2 = 64055.0`, so the basis at the first instant is `55.0` USDT
per BTC, or `55.0 / 64000.0 * 10,000 = 8.59` basis points.

## 3. How the fixture is built

Two formulas, and a venue-specific half-spread:

```text
btc_mid(i)  = 64000.0 + 40.0 * sin(i / 30.0)
binance_mid = btc_mid(i)
bybit_mid   = btc_mid(i) + 55.0 + 45.0 * sin(i / 45.0)
```

- Both venues carry the same 40 USDT amplitude sine, so both move together. That is the "same
  economic thing".
- The BYBIT price is shifted by a basis of `55.0 + 45.0 * sin(i / 45.0)`, which oscillates between
  10 and 100 USDT. That is the "priced differently in two places".
- The half-spread is 0.5 USDT at BINANCE and 0.8 USDT at BYBIT, so the executable spread is always
  smaller than the mid spread, and by a different amount at each venue.

The resulting basis in basis points over the whole file: minimum 1.56, mean 9.16, maximum 15.62.
Those three numbers are the range your entry and exit thresholds must live in.

## 4. Timestamps and how to align two venues

Both files use integer nanoseconds since the Unix epoch, which is the unit every NautilusTrader
timestamp uses. The grid is:

```text
first : 1700000000000000000   (2023-11-14T22:13:20Z)
step  : 1000000000            (1 second)
last  : 1700000239000000000   (2023-11-14T22:17:19Z)
```

In this fixture row `i` of one file has exactly the same timestamp as row `i` of the other, so the
alignment is already done for you. Real venues do not behave that way: two exchanges never stamp a
book update at the same nanosecond. Alignment is therefore a decision you must make and record.
There are three honest options:

1. **Fixed grid, forward fill.** Sample both books at a fixed interval, for example once per
   second. If a venue did not update within the interval, carry its last known quote forward and
   record that you did so. Cheap, and it can invent a spread that no participant could have hit.
2. **Fixed grid, last event at or before the grid point.** Use the most recent quote at or before
   each grid point, and require both venues to have one. This is the same as forward fill but with
   an explicit tolerance, so a venue that has not ticked for ten minutes is detectable.
3. **Exact timestamp join.** Keep only timestamps that both venues published. Accurate, and it
   silently discards most of the data.

Whichever you choose, record it next to the data. A basis computed on a one-second grid and a basis
computed by exact join are different series, and a strategy tuned on one will misbehave on the
other. `docs/design/relative_value_screening.md`, section 2.8, makes the same point about reusing
one spread with three different windows: the spread is defined by the convention, so the convention
is part of the definition.

The engine processes one event at a time. Even when two quotes share a timestamp, you receive two
callbacks. Lecture 03 showed that cost directly: with two quotes per second, the first five printed
lines contained two pairs of prints that recomputed a spread from one fresh and one stale quote.
Lecture 05 acts only when the two venues' `ts_event` values are equal.

## 5. How it would come from a real venue

Real top-of-book data arrives as a stream. For each venue:

1. Subscribe to the instrument's book ticker, or to order book deltas and build the top of book
   yourself. `QuoteTick` is the model type for the result, and
   [`../../concepts/data/quote_tick.md`](../../concepts/data/quote_tick.md) describes its fields.
2. Record the venue's own event timestamp, not your machine's clock. The venue timestamp is
   `ts_event`; your receipt time is `ts_init`. Historical data uses the same two fields.
3. Store the best bid, best ask, and their sizes.
4. For a perpetual future, also record the funding rate as a `FundingRateUpdate`, and the mark and
   index prices as `MarkPriceUpdate` and `IndexPriceUpdate`. These are reference data: receiving one
   does not mean a trade happened, and a funding rate does not mean a payment was applied. The
   engine applies the payment when the funding boundary is reached, which is described in
   [`../../concepts/data/funding_rate_update.md`](../../concepts/data/funding_rate_update.md).
5. Resolve the timestamp convention, per section 4 above.

The unit tests in the project ship no committed crypto top-of-book fixture for these two venues, so
a real study needs your own recording. The repository does ship an order book delta fixture at
`crates/adapters/tardis/test_data/csv/deltas_1.csv`, which is a realistic book shape if you want to
build a top of book from deltas.

## 6. Inspecting the files

Save this program outside the repository, for example `C:/scratch/cross_venue_inspect.py`, and set
`DATA` to your copy of the `sample_data` folder.

```python
"""Inspect the two venue files and check that their timestamps align."""

import csv
from decimal import Decimal
from pathlib import Path

DATA = Path(
    "D:/Users/vince/PycharmProjects/nautilus_trader/docs/usermanauls/cross-venue-relative-value/sample_data",
)
FILES = {
    "BINANCE": "btcusdt_perp_binance_quotes.csv",
    "BYBIT": "btcusdt_perp_bybit_quotes.csv",
}


def read_rows(filename: str) -> list[dict[str, str]]:
    with (DATA / filename).open(encoding="ascii", newline="") as f:
        return list(csv.DictReader(f))


for venue, filename in FILES.items():
    rows = read_rows(filename)
    print(f"{venue} {filename}: {len(rows)} data rows, columns={list(rows[0])}")
    for row in rows[:3]:
        print("  ", row)
    print("   ...")
    for row in rows[-1:]:
        print("  ", row)

binance = read_rows(FILES["BINANCE"])
bybit = read_rows(FILES["BYBIT"])

binance_ts = [row["ts_event_ns"] for row in binance]
bybit_ts = [row["ts_event_ns"] for row in bybit]
print(f"identical timestamps: {binance_ts == bybit_ts}")
print(f"first ts_event_ns: {binance_ts[0]}, step ns: {int(binance_ts[1]) - int(binance_ts[0])}")

spreads = []
for row_b, row_y in zip(binance, bybit):
    mid_b = (Decimal(row_b["bid_price"]) + Decimal(row_b["ask_price"])) / 2
    mid_y = (Decimal(row_y["bid_price"]) + Decimal(row_y["ask_price"])) / 2
    spreads.append((mid_y - mid_b) / mid_b * Decimal(10_000))
print(f"spread_bps: min={min(spreads):.2f} mean={sum(spreads) / len(spreads):.2f} max={max(spreads):.2f}")
```

## 7. Reading the data by hand

Take row 0 of both files:

|     | BINANCE | BYBIT   |
| --- | ------- | ------- |
| Bid | 63999.5 | 64054.2 |
| Ask | 64000.5 | 64055.8 |
| Mid | 64000.0 | 64055.0 |

- Basis in money: `64055.0 - 64000.0 = 55.0` USDT per BTC.
- Basis in basis points: `55.0 / 64000.0 * 10,000 = 8.59` bps.
- Executable basis if you sell BYBIT and buy BINANCE: `64054.2 - 64000.5 = 53.7` USDT.
- That is `53.7 / 64000.5 * 10,000 = 8.39` bps. The mid said 8.59; the trade offers 8.39.

On a trade size of 1.000 BTC:

```
gross on the touch = 53.7 USDT
binance taker fee  = 0.0004 * 64000.5 = 25.6002 USDT
bybit taker fee    = 0.0006 * 64054.2 = 38.4325 USDT
net                = 53.7 - 25.6002 - 38.4325 = -10.3327 USDT
```

The first observation of the file is a losing trade at these fee rates. Lecture 05 shows that the
whole file, traded naively, loses as well, and lecture 06 explains exactly where the money goes.
